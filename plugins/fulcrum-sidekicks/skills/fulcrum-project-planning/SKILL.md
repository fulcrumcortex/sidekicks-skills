# Plan work with acceptance evidence

Start with the intended outcome, constraints, current work and the requested planning horizon. Check existing issues before adding duplicates. Use the user’s current project tool; do not migrate a team or create a new platform as part of planning.

Break work into units that produce reviewable results. For each, specify the outcome, input, dependency and acceptance evidence. Use an owner or date only when stated or authorised; otherwise mark it undecided. Avoid implying that an estimate is a commitment.

Identify which work can proceed independently and which depends on a decision, access or another artifact. Keep risks concrete and tied to the plan rather than adding generic checklists.

If issue creation is requested, confirm the project and permissions, create only the agreed scope and inspect the saved fields. Do not change a team-wide workflow or close unrelated issues. A board status is a coordination signal, not evidence that a release reached production.

Return the linked plan or issue list, dependencies, acceptance criteria and open decisions. For completed work, attach actual checks and destination evidence instead of merely moving a card to Done.
